# 调研报告

目标：产出**读完就能拍板**的报告——每个结论都有信源、有时效、有分歧披露，而不是一堆检索结果的摘抄。

## 什么时候用

适用：技术选型对比、竞品/主流方案对标、可行性评估、某领域现状综述。
不适用：答案在本仓库代码里（直接 `search_code` / `read_file`），或用户只要一句结论（直接答，别铺开写报告）。

## 流程

### 1. 先对齐问题（别跳过）

动手检索前，把要回答的问题写成 **3～6 条具体子问题**，用 `update_tasks` 落成清单。
子问题必须可证伪，例如「X 的定价模型是什么」而不是「X 好不好」。

**范围有歧义时先问用户**——用 `ask_user` 确认取舍口径（比如"对比是看成本还是看上手速度"）。
调研做完才发现问错方向，是这类任务最大的浪费。

### 2. 检索：先立事实，再找争议

对每个子问题：

1. **先取一手信源**：官方文档、规范原文、发布公告、源码仓库、论文。用 `web_search` 找入口，`web_fetch` 读正文。
2. **再取交叉验证**：至少 1 个独立于官方的信源（第三方评测、实证研究、用户报告）。**官方说的能力和实际表现要分开记。**
3. **主动找反面证据**：明确搜一轮"局限 / 问题 / criticism / limitations / 踩坑"。只有优点的报告没有决策价值。

信源分级与反爬对策见 [references/SOURCING.md](references/SOURCING.md)。

**边查边记**：每确认一个事实就用 `update_notes` 补进「## 已确认事实」，附来源 URL 和日期。
这样上下文被压缩也不丢证据，最后写报告直接从笔记攒。

### 3. 量大时并行委派

子问题彼此独立且各自要读好几篇资料时，**同一回合发多个 `delegate`**（role 用 `researcher`，只读、并行安全）：
一个子 Agent 查一个子问题，回来的是摘要不是原文，主上下文不会被撑爆。

汇总时注意：子 Agent 之间不知道彼此的发现，**冲突要由你来对账**（见下一步）。

### 4. 处理冲突与时效

- 两个信源打架：**不要挑一个信了事**。写明双方说法、各自来源与日期，给出你判断更可信的一方及理由。
- 一切结论标注**信息时点**。技术类信息半年就可能过时——明确写"截至 YYYY-MM"。
  **别凭印象写年份**（很容易写成训练语料里的年份）：不确定今天日期就跑一下 `date` 确认再写。
- 找不到可靠信源的问题，**如实写"未找到可靠信源"**，不要用常识补位冒充调研结论。这条没有例外。

### 5. 成稿

用 [assets/report-template.md](assets/report-template.md) 作骨架，`write_file` 落到工作区。
结构要点：

- **结论先行**：开篇 3～5 句直接给答案和建议，不要让人读到第三页才知道结果。
- **每个结论段末尾附来源链接**，格式 `[标题](URL)`。
- **对比用表格**，维度选能影响决策的（成本、上手门槛、锁定风险、维护活跃度），不要凑数。
- **风险与未知单独成节**，包括你没查到的部分。

### 6. 自检（必做）

```
python3 <技能目录>/scripts/check_report.py <报告文件路径>
```

脚本检查：结论段是否有来源链接、来源是否重复凑数、是否残留 TODO/占位符、是否标注了信息时点、
是否有"风险/局限"一节。**报错就改到通过再交付**，别把自检失败的稿子交出去。

脚本不检查内容对错——事实准确性靠上一步的交叉验证，不靠脚本。

## 常见失败模式

| 症状 | 纠正 |
|---|---|
| 通篇"某某认为""业界普遍" | 换成具体信源 + 链接；说不出是谁说的就删掉 |
| 只有优点 | 回到第 2 步补搜一轮局限与反面案例 |
| 罗列检索结果不给判断 | 每节末尾加一句"这对本次决策意味着什么" |
| 抄了官方营销话术 | 区分"官方声称"与"实测/第三方验证" |
| 报告长但没结论 | 结论先行，正文压到支撑材料的角色 |
