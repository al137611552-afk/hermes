# 信源分级与取材对策

## 信源可信度分级

按可信度从高到低，写报告时优先取上层，并在报告里标明层级：

1. **一手规范/官方文档/源码** —— 规范原文、API 文档、发布公告、代码仓库。
   事实性问题（字段定义、限制、定价、版本）**只认这一层**。
2. **同行评议研究/实证测量** —— 论文、基准测试、大规模实证study。
   用于"实际效果如何"这类官方不会告诉你的问题。注意看样本量和测量方法。
3. **有署名的独立技术分析** —— 有具体作者、有可验证细节、给出方法论的第三方文章。
   用于交叉验证，不单独作为事实依据。
4. **社区讨论/问答** —— Issue、论坛、问答站。
   只用来发现问题线索和踩坑方向，**不作为结论依据**，找到线索后回到第 1、2 层求证。
5. **二手转述/营销内容** —— 聚合博客、SEO 文章、厂商白皮书。
   基本不可用。唯一价值是顺着它找到原始出处，然后引用原始出处。

**判断口诀**：这句话如果错了，谁会为它负责？没有答案的信源就是第 5 层。

## 取材对策

### 优先级顺序（成本从低到高）

1. **官方 API / 数据导出** —— 治本。有 API 就别爬页面。
2. **`web_search` + `web_fetch`** —— 默认路径，公开页面够用。
3. **浏览器穿透（Playwright MCP）** —— 页面要 JS 渲染、要登录、或 `web_fetch` 拿到的是空壳时用。
   有头模式下可让用户手动登录/过验证，持久 profile 复用登录态。
4. **停下来问用户** —— 需要账号、付费墙、或站点明确禁止抓取时，用 `ask_user`，别自己硬闯。

### 反爬：不要硬刚

遇到验证码、频率限制、指纹检测，**军备竞赛必输**。正确顺序是：
找官方 API → 找数据导出 → 用登录态复用 → 问用户要资料 → 如实报告"该信源取不到"。

**明确禁止**：绕过付费墙、伪造身份、破解验证码。取不到就在报告里写取不到，这不丢人。

### 浏览器穿透注意

- `snapshot` 返回空 ≠ 页面没加载，可能还在渲染——先 `wait_for` 再 snapshot。
- 已经拿到搜索结果列表就**点进具体结果读内容页**，不要换个搜索引擎重搜一遍。
- 穿透模式下 `web_search`/`web_fetch` 会被移除，这是刻意的：逼你走完"导航 → 点击 → 读内容"，
  不要在浏览器里读不动就想绕回外部搜索。

## 引用记录格式

在 `update_notes` 的「已确认事实」里按这个格式记，成稿时直接搬：

```
- 事实：Agent Skills 规范于 2025-12-18 开放为公共标准
  来源：https://example.com/announcement （官方公告，一手，读取于 2026-08-07）
  交叉验证：https://example.com/analysis （第三方分析，与官方一致）
```

三个要素缺一不可：**事实、来源 URL、读取日期**。日期决定了这条结论多久后需要复核。
