# ADR 0022 — 交互式命令：不做全局 auto-yes，做一条看得见的应答通道

- 状态：**已接受**（2026-08-11）
- 日期：2026-08-11
- 相关：ADR 0021（产物与句柄，后台进程输出的落盘）、FR-10.3（后台命令/长进程）

## 背景

真机反馈：`run_powershell` 经常跳「命令超时（>180s）已终止」。用户的问题很直接——
**「碰到交互式任务 hermes 不能默认 yes 吗？不然必定卡超时。主流 agent 怎么处理？」**

盘完现状：hermes 早就有一层非交互硬化（`-NonInteractive`、`stdin=DEVNULL`、
`GIT_TERMINAL_PROMPT=0`/`PAGER=cat`/`DEBIAN_FRONTEND` 等），所以**多数**交互命令是拿 EOF 快速失败，
并非"必定挂满 180s"。真正会挂满的是两类：

1. **不会自己退出的常驻程序**（dev server / watch / GUI / 安装向导）——已有 12s 探针兜底；
2. **绕过 stdin 直接读控制台的**（Windows 的 `pause`/`choice`、部分安装器）——`DEVNULL` 挡不住。

但确实缺了一半：撞上了只回一句笼统超时，模型无从改写命令，用户也无从介入。

## 主流做法（调研）

| 路子 | 代表 | 机制 |
|---|---|---|
| A 非交互硬化 + 逼模型加 `-y` | Claude Code、Codex CLI、Gemini CLI | 无 TTY、stdin 不接、超时即杀；提供后台运行 + 读输出/杀进程的配套工具。**都不自动回答提示** |
| B 真终端交给人接管 | Cursor、Windsurf、VS Code Copilot agent | 命令跑在用户可见的集成终端里，卡住时用户自己敲 |
| C 持久会话 + 允许写入运行中的进程 | OpenHands（bash 工具的 `is_input`）、Devin（真 VM） | agent 看到提示后自己回一行 |

## 决策

**三条，按优先级：**

### 1. 不做全局 auto-yes（拒绝 `yes |` / 无条件喂 y）

确认框正是防误删的最后一道闸：`git clean`、`npm publish`、`Remove-Item -Recurse` 问的那句"确定吗"，
恰恰是用户最需要看见的时刻。全局 auto-yes = 把 hermes 的权限 gate 从背后掏空。
**同理不注入 `$ConfirmPreference='None'`**——那是在改用户命令的语义，属于偷偷替他点"是"。

### 2. 先走 A：能不交互就别交互

- 补齐非交互环境变量（npm/ssh/gh/dotnet/composer/husky/CI…），让命令**根本不问**；
- 会改语义的开关（`CI`、`GIT_SSH_COMMAND`）用 `setdefault`，用户显式设过就尊重；
- 工具描述里明说「执行环境无终端、stdin 已关闭」，让模型先手加 `--yes`，而不是撞一次再改；
- 真撞上了就**认出提示并点名原文**（`looks_waiting_input`），把"笼统超时"换成"你卡在这句话上"。

### 3. 再走 C（而非 B）：一条通道，两个入口

**不做 B 的完整集成终端**（ConPTY + xterm.js）：要引新的原生依赖、要处理 ANSI/尺寸/编码，
而且真 PTY 会让一堆命令切回交互模式（进度条、分页器、颜色），与第 2 条的非交互硬化直接对着干。
用户要的从来不是"一个终端"，是"卡住时能敲个 y"。

所以：**后台进程 `stdin` 开 PIPE，加一条写入通道，两个入口共用**——

| 入口 | 谁在敲 | 是否过权限 gate |
|---|---|---|
| `write_process_input` 工具 | 模型 | **是**（dangerous，每句输入都让用户看清写的是什么） |
| 工具块里的行内输入行 | 用户 | **否**（用户自己就是授权，再问一遍是纯噪声） |

## 关键实现约束

1. **提示必须先看得见**。交互提示**不带换行**（`Ok to proceed? (y) `），原来前台读
   `TextIOWrapper.read(4096)`（阻塞到读满/EOF）、后台按行迭代（`for line in stdout`）——两条路
   都会把提示压在缓冲里。改成二进制 `read1()` + 增量解码。
   *顺带修好*：前台"实时流输出"因此一直不实时（输出攒不满 4096 字符就只在退出时一次性吐出）。
2. **判据保守**：认定"在等输入"要三条同时成立——进程还活着 + 输出**最后一个非空行**像提示 +
   已静止若干秒。只靠模式匹配会误伤（`--help` 里就有 `[y/N]`、日志里也有 `Password:`）。
   前台阈值 5s（判错要杀进程，代价大），后台 2s（判错只是多给一句提示）。
3. **前台不等人**。前台识别到提示就**杀掉**并给出两条出路（先劝非交互写法，再给"起后台再回答"），
   **不做"暂停计时等用户输入"**——`/crazy` 无人值守跑一夜，卡在提示上等人等于白跑。
   人接管只存在于后台通道：进程在那儿挂着不消耗任何人的等待。
4. **写入要回显**。进程拿不到 TTY 不会自己回显输入，那就由我们把 `[已输入] y` 补进输出缓冲和产物日志，
   否则事后翻记录看不出这个 `y` 是谁答的。
5. **一次一行**。`write_process_input` 拒绝多行文本：多行会把后续几个提示一股脑答掉，
   用户在确认条上也看不清到底答应了什么。
6. **只读角色不能写**（researcher/reviewer/tester）：写输入是有副作用的动作，走白名单自然排除。

## 备选与不选的理由

- **全局 auto-yes / `yes |` 管道**：见决策 1，掏空权限模型。
- **完整集成终端（B）**：成本高、与非交互硬化冲突，且一旦有"终端"用户就会期待通用终端语义
  （cd、历史、Ctrl+C、多标签），支持面积失控。
- **前台等人（暂停超时计时）**：与无人值守模式冲突，见约束 3。
- **给前台命令也开 stdin**：前台没有句柄可寻址，模型/用户都无从"对着它说话"；
  真需要交互就该走后台形态，这也让"哪些命令是交互式"变成一个显式决定。

## 已知限制

- 行内输入行**只在模型调用 `read_process_output` 拿到提示时**才会出现（没有后台看门狗主动上报）。
  模型不轮询，人就看不到入口。后续可加一个"进程转入等待态就发事件"的观察者。
- 只覆盖 stdin 文本提示。真正需要 TTY 的程序（全屏 TUI、密码输入用 `/dev/tty` 的）仍然不行——
  这类应当改用非交互写法或换等价命令。
- 提示识别是启发式，会有漏判（提示文案不在模式表里）。漏判的代价是退回原有的超时行为，不会更糟。
