# ADR 0027 — 评测语料分层与录制回放（喂饱评估内核）

- **状态**：提议（2026-08-19），待实现。分期见文末「交付分期」。
- **相关**：ADR 0014（评估/策略分层架构）、ADR 0015（Error Taxonomy）、ADR 0016（World State /
  Failure Memory）、ADR 0017（Learning Engine）、ADR 0019（评审 gate 禁模糊分——本文沿用同一条纪律）；
  代码锚点 `scripts/eval/`、`tests/golden/`、`src/agentcore/agent/world_state.py`、`src/agentcore/providers/`
- **来源**：与 deepseek-harness 横向对比后的结论——**hermes 的评估/策略内核（块 A–H）建得比对方完整，
  但它在空转**。进一步读码发现问题不是"没有语料"，而是**语料在产生、却落不了盘，且指纹是脏的**。

## 背景

块 A–H 已经交付了一整套评估内核：`contract.py`（Need 9 枚举）、`evaluators/`（Coding/Search/Shell）、
`taxonomy.py`（ErrorClass 9 类）、`world_state.py`（WorldState + FailureMemory）、
`learning/engine.py`（aggregate → propose → StrategyStore，approve 强制 `golden_passed=True`）。

设计是对的。问题在**输入端**。2026-08-19 读码查证到的硬事实：

| 事实 | 后果 |
|---|---|
| `loop.py` 已 emit 八种 nudge 事件（`login_hint` / `stuck_hint` / `search_hint` / `deadend_hint` / `research_hint` / `truncation_hint` / `learning_shadow` / `learning_advice`），`_emit_result` 还附 `eval`（含 `error_classes`） | **遥测已经齐了**，每一跑都在流过，只是没人接 |
| `harness.py:EvalResult` 只活在内存里，`run_eval.py` 只打印 + 退出码 | 跑完即失，**两次跑无法对比** |
| `world_state.py:fingerprint()` 的 `_KEY_PARAMS` 含 `path` / `file_path` / `command`，而评测在 `tempfile` 建工作区 | **同一个失败，两次跑得到两个不同指纹** |
| `conversation.py:2279` 把 FailureMemory 硬编码到 `ROOT/data/failures.db`；`harness.py` 没关 `agent.failure_memory`（`config.py:130` 默认 `True`） | 评测语料与真实使用语料**混在一个库**，无法分开分析、无法重置重跑 |
| `scripts/eval/tasks.py` 只有 6 个任务；`tests/golden/cases.py` 有 51 条 / 13 类 | Golden 单元层健康，**端到端层量级不足**，中间缺一层 |

指纹污染这条最隐蔽，值得展开：`aggregate()` 按 `error_class` 归并、`paths` 记 distinct 指纹数，
而 `propose(min_count=3, min_paths=2)` 是**双门**。临时路径进指纹之后，同一个失败在 N 次跑里变成
N 条不同的"路"——`paths` **虚高**（假信号越门）、每指纹 `total` **恒 1**（真信号被拆碎、越不过 `min_count`）。
**两个方向同时错**。这不修，攒得再多也是脏语料。

> 待办第二档里已记过半条：「失败语料无来源标记：评测/测试失败混进 FailureMemory → 要改 SQLite schema」。
> 本 ADR 把它与指纹归一合并处理——**来源标记解决"混"，指纹归一解决"碎"，缺一不可**。

## 决策 1 — 语料分三层，各司其职，不互相冒充

| 层 | 是什么 | 成本 | 进 CI | 守什么 |
|---|---|---|---|---|
| **L-Golden**（V0 前 51 条 / 13 类） | 决策函数的 `输入 → 期望输出`，离线确定性、不调模型 | 毫秒 | ✅ 每次 | 决策内核不回归 |
| **L-Cassette**（新） | 录好的模型输出重放，跑完整 loop | 秒级、离线 | ✅ 每次 | **端到端行为**不回归 |
| **L-Live**（扩量） | 真模型真网络跑任务集 | 分钟级、烧 key | ❌ 按需 | **解题率**的绝对水平与 A/B |

三层**不可互相替代**，写清楚免得将来偷懒合并：

- Golden 测不到 loop 的组合行为（两个 detector 同轮都触发会怎样，只有跑完整 loop 才知道）；
- Cassette 测不到"换个模型/改了提示词之后还行不行"（模型输出是录死的）；
- Live 因为有模型随机性，**单跑一次的 pass/fail 是伯努利采样**，不能当回归门。

## 决策 2 — 指纹按工作区相对路径归一；语料按来源分库

**指纹归一**：`fingerprint()` 增加 `workspace` 参数，路径类关键入参（`path` / `file_path`）先转
工作区相对路径，`command` 内嵌的绝对路径同样归一，再取 sha1。纯逻辑不变、无 IO。

**分库**：`FailureMemory` 路径改为可注入。真实使用 `data/failures.db`，评测 `data/failures.eval.db`。

**为什么分库而不是只加一列 `source`**：加列能区分，但**不能重置**。评测要能"清空重跑一批"，
而真实使用的死路记忆是跨会话资产、绝不能被评测流程误删。两个生命周期不同的东西不该共用一个文件——
与 ADR 0025 决策 7（`usage.db` 独立、不进 `hermes.db`）同一条理由。`source` 列仍然加，用于库内细分
（评测 / 自检 / 真实），但**隔离靠分库**。

## 决策 3 — 每次评测跑必须落 Run Record，且自带可比性三件套

`EvalResult` 落 `data/eval_runs/{run_id}/{task}.json`。除已有字段外**必须**记：

1. **git sha**（被测代码是哪一版）
2. **模型档案 + 真实 model id**（`active_model` 是别名，会漂）
3. **配置快照**（影响行为的 `agent.*` 全量：`max_steps` / 各 detector 阈值 / `crazy_*` / 预算上限）

**没有这三样，两份记录不可比**——这是本项目已经踩过的坑的同款：ADR 0025 决策 3 立过
「一个自信的错数比缺失更危险」，两份不可比的记录放一起做对比，产出的就是自信的错数。

`run_eval.py` 增 `--out` / `--repeat N` / `--tag`；新增 `scripts/eval/report.py` 吃两个 run_id 出对比表。
对比表的列**全部从现有事件流直接算**，不改 `loop.py`：

pass@1 / pass@N ｜ 步数 ｜ 工具调用数 ｜ 子任务数 ｜ **八类 nudge 各自触发次数** ｜ 错误分类分布 ｜ 耗时 ｜ token

倒数第四列是 V5 的唯一输入。

## 决策 4 — 录制/回放挂在 provider 层；miss 必须报错，**绝不静默回落真跑**

`providers/base.py:BaseProvider.stream_chat` 已经是统一接口，在 `build_provider()` 外包一层即可，
**不动任何 provider 实现**：

```
RecordingProvider(inner)   真跑 + 落 (请求指纹 → StreamEvent 序列)
ReplayProvider(cassettes)  离线按指纹取回放
```

- **cassette key** = `sha1(model_id + system + messages_json + tools_json)`；messages 里的图片用
  blob hash 代替内容（否则同一张图不同编码会分裂成两个 key）。
- **存** `data/cassettes/{task}/{key}.jsonl`，一行一个 `StreamEvent`。
- **miss 必须硬报错并指出第几步 miss**。静默回落真跑会同时犯两个错：偷偷烧 key，以及把
  "我的改动让轨迹发散了"这个**最有价值的信号**当噪声吞掉。同 ADR 0025 决策 3 的立场——宁缺勿假。

**为什么不做更聪明的模糊匹配**：cassette 的价值全部来自"模型输出逐字固定"这一条。一旦允许近似匹配，
回放就不再是回放，A/B 的对照组也就不成立了。

### 实现 V3 时对本条的三处补充（2026-08-19）

**① 录音必须落在 `finally` 里。** `AgentLoop.run` 收到 `done` 事件就 `break`，包装生成器
被丢弃，`for` 之后的语句永远不执行——第一版就是这样录出 0 条的。且**只在看到 `done` 时才写**：
半截录音比没有更坏，回放时它会假装那轮正常结束、把"当时其实炸了"抹掉。

**② 指纹要折掉工作区绝对路径。** 工具输出会**回灌进消息历史**（pytest 的
`rootdir: /tmp/tmpXXXX/ws`），临时工作区每跑都不同 → key 每跑都变 → 全 miss。
与决策 2 的死路指纹同病同药。

**③ 注入文案里不能嵌跨跑可变状态——这条是本决策真正的隐藏前提。**
死路提示写的是「这条路已累计 **N** 次失败」，N 来自跨会话的 `FailureMemory`。共用一个库时
它每跑都涨，于是 (a) cassette 永远 miss，(b) **反例任务随语料增长逐渐开始误报**、基线一路漂。
故评测**默认每跑一个独立的失败记忆库**；要为块 V4 攒语料才显式共用（`--accumulate`）。

推论，值得单独记住：**"replay 是回归门不是 A/B 工具"这条限制比原文写的更紧**——
连注入文案里的一个数字都足以让全部录音失效。任何把可变全局状态写进模型可见文本的设计，
都会同时损害可回放性与可重复性。

**⑤ 请求指纹要抹掉「零信息的运行时噪声」——这不是"模糊匹配"，但边界必须写死。**

禁止模糊匹配的本意是：**不把不同的请求匹配到同一份录音**。而有些记号在同一情形下
必然变化、却不携带任何语义，抹掉之后两个请求是**真的相同**、不是"差不多"：

| 抹 | 为什么 |
|---|---|
| 工作区绝对路径 | 临时目录名每跑不同；路径本身不是内容 |
| 堆地址 `0x7c258c2e0360` | pytest 断言自省会打出来；每个进程都不同，且不同也不代表任何差别 |
| 测试耗时 `in 0.09s` | 度量的是**本机当时的调度快慢，不是被测代码的行为**；且我们**不希望**模型行为取决于测试跑了 80ms 还是 90ms |

| **不抹** | 为什么 |
|---|---|
| 时间戳 | "某时刻的日志"可能是有意义的内容 |
| git SHA | 它**标识内容本身** |
| 一般的小数+s | 正文里的 "超时设成 1.5s" 是有意义的配置值——故耗时模式收窄到 `in <小数>s` 这一个搭配 |

**这已经是第二次放宽（V3 收尾时为 pytest 耗时）。每放宽一次都在侵蚀这条线，
故：再要加新模式必须是显式决策，且要能论证该记号「机器生成 + 标识临时运行态 +
同一情形下必然变化 + 零语义」四条同时成立。** 不满足的任务走 `replayable=False`。

**⑥ 有意行为变更后，优先「回放刷新基线」而不是重录**（块 V4a 加 `--refresh-baseline`）。

重录会把**新的模型轨迹**一起换掉，于是"代码改动的效果"与"模型这次的发挥"混在一起、谁也说不清。
回放已经把模型输出焊死，此时刷新基线得到的差异**只可能来自我们自己的代码**——这正是决策 4
存在的理由，也是块 V5 调阈值时唯一能用的对照方式。

三条纪律（焊在实现里）：①只能配 `--replay`；②**miss 时拒绝刷新**——轨迹都没跑通，
基线就无从谈起，那种情况必须重录；③逐项打印基线变化，**不许静默改绿**。

边界：刷新的前提是"这次行为变更是有意的"。它不是让门变绿的工具，是让门**跟上一次已定的变更**
的工具；判断"该不该变"仍然是人的事，脚本只保证变化被看见。

**④ 录音存 `tests/cassettes/` 而非 `data/cassettes/`**（偏离原文）：`data/` 在 `.gitignore` 里，
CI 拿不到就谈不上"进 CI"。同目录放一份**不含密钥**的 `model.yaml`——
cassette 的指纹里嵌了 model id，录音与档案是绑定的，分开放两处迟早对不上。

## 决策 5 — 判分优先程序化；不得已用模型判分**必须多数投票**

沿用现有 `check(ws, result) -> (bool, str)` 签名。优先级：跑测试 > 查文件/git 状态 > 查事件流 > 模型判分。

模型判分**必须 3 次取 2**。理由与 ADR 0019 禁用"共识度 80%"是同一条：**判分器自己的方差会淹没
被测对象的差异**。一个方差比信号大的判分器，比没有判分器更糟——它会让你相信噪声。

## 决策 6 — L2 任务必须**正反成对**，反例优先于正例

每个 detector 至少两个任务：一个**该触发**、一个**不该触发**。

**反例比正例更重要**，因为代价不对称：漏报只是少一次帮助（模型多半还能自己走出来），
**误报是浪费一整轮 + 用一段权威口吻的注入把模型从正确的路上推开**。而现在这些阈值
（`detect_repeated_failure(threshold=2)`、`detect_low_quality_research(max_nudges=1)`、
研究催重搜的全局预算）**全是拍脑袋定的，误报率是零测量**。

同一条延伸到 V5 的验收判据：**触发得准 ≠ 有用**。第三个指标是「触发后那一轮 `Evaluation.issues`
是否减少 / Need 是否前进」——判据现成，`eval` 事件里就有。

### 实现 V2 时对本条的两处修订（2026-08-19）

**① 正反例的判据必须不对称。** 原文写"每个 detector 一对"，隐含两边同权重，实现时确认那是错的：

| | 判据 | 为什么 |
|---|---|---|
| 反例（不该触发） | **硬断言，误报即 FAIL** | 条件不成立时 detector 永远不该响，这是**确定性的**，与模型走哪条路无关 |
| 正例（该触发） | **软观测，只记触发率、不判 FAIL** | 漏报取决于模型愿不愿意走那条坏路，**逼不出来**；硬判会把"模型这次表现好"误记成"detector 坏了" |

正例的真实价值在**触发率**（`report.py` 的 `nudge.*` 列），不在单次通过。
**反例是门、正例是仪表。**

**② 反例不必"一个 detector 一个任务"。** 一个正常任务里**所有** nudge 都不该响，
用 `{"*": False}` 一行表达比拆成八个任务更强（覆盖面更全）也更省（少跑七次模型）。
正例任务同样带 `"*": False`——否则测不出"观测目标响了、但旁边那些也乱响"。

**③ 夹具必须先过启用门。** detector 多数有前置开关（`search_nudge_files` 默认 40 个代码文件、
`stuck_edit_threshold`、`trace_run` 是否可用）。夹具没越过门槛，那个正例就是**哑弹**——
看着有覆盖，其实 detector 压根没被启用。V2 的任务自检里为此专门钉了两条
（正例必须越门、反例必须低于门）。

## 决策 7 — Learning 候选仍须人审 + Golden 门（重申，不改）

语料喂饱之后会有人想加自动采纳。**不做**。理由 ADR 0014/0017 已立，`trajectory.py` 里也论证过同一件事
（"判据不可靠：保守则永不触发，激进则批量生成垃圾"）。`StrategyStore.approve` 强制
`golden_passed=True` 这道硬门保持不变。

**喂饱的定义是"让 `propose()` 产出有证据的候选"，不是"让候选自动上线"。**

## 决策 8 — 联网侧：**世界**必须与模型侧一起定死（实现批 2 时增补，2026-08-19）

**决策 4 只解决了一半。** cassette 包在 `build_provider()` 外面，固定的是**模型侧**；而
`web_search` / `browser_*` 的**工具输出来自真实网络**，它会随 tool_result 回灌进消息历史 →
进请求指纹（与决策 4 补充②「工作区路径污染指纹」是同一个机制）。真网结果每跑一变，
指纹就每跑一变，**回放必 miss**。ROADMAP 原先写批 2「等 cassette 落地后再做」，
这个前提只成立一半。

**故：联网侧的 L2 任务用「桩世界」——一组纯函数桩工具替代真实世界**（`scripts/eval/world.py`）。

- **桩必须继承真工具**（`StubWebSearch(WebSearchTool)`），只换 `run`。
  name / description / input_schema 会进 system prompt、也就进请求指纹；桩若自造描述，
  桩跑与真跑就不是同一个请求，两边结果不可比。有测试逐字钉住。
- **输出必须与真工具逐字同构**（表头 `[搜索结果·引擎] query` + 行首 `N. `）——
  `ResearchEvaluator` 靠这个格式切条目，格式一偏，**任何**预算判定都不成立、正例变哑弹。
- **不起本地 HTTP 服务**（虽然那样能多覆盖一层真实解析）：随机端口号会进消息历史，
  就得再往决策 4 的归一化里加一条模式——那条线已经放宽过两次，为一个桩付这个代价不值。
  真实解析链路由 `network=True` 的真跑任务覆盖。
- **`world` 与 `network` 互斥**：装了桩就不许标 network（标了会被 `--offline` 跳过，
  永远进不了 CI 门）。有测试钉住。

**保真度论证**：这三个 detector（`research_hint` / `login_hint` / `truncation_hint`）的输入
**本来就只是那段工具输出文本**——对它们而言假世界与真世界无差别。桩换掉的是"世界会不会
给出那种坏输入"，而这正是批 1 真跑暴露的病根（三个正例触发率全 0＝夹具压力不够，成了哑仪表）。
**剩下的不确定性只有"模型愿不愿意走那条路"，那是漏报侧，本来就逼不出来**——故正例仍是软观测
（决策 6 不变），但夹具保证**一旦走上那条路就必然触发**。

### 真跑录制时对本条的两处修订（2026-08-19）

**① 桩世界必须连 shell 一起封。** 只封 web/browser 是不够的——真跑实测：检索零进展时模型会
改用 `run_bash` + curl **自己爬真网**，桩当场形同虚设（41 次工具、213s、回放第 8 步 miss）。
故 `Task.deny_tools`；`"shell"` 由 harness 解析成当前平台的 `run_bash`/`run_powershell`，
**摘不到就抛错**（静默摘不掉＝以为封住了其实没封，比不封更坏）。

推论，比这次的修复更值钱：**"世界"的边界是按能力算的，不是按工具名算的。**
任何能触达外部的工具（shell、未来的 MCP server）都在边界内，漏一个整个封闭性就不成立。

**② 夹具越不像夹具，测到的才越是真行为。** 模型一眼认出 `example-*.com` 是示例域名、
又发现不同关键词返回完全相同的结果、不同 URL 导航到同一页面，于是判定「环境无法访问真实
互联网」，转而声明数据不可采用。**那是正确的职业操守**（H3c 接地闸想要的正是这个），
但任务也就测不到想测的东西了。故：域名用看起来正常的名字；**浏览器桩回显实际请求的 URL**
（真浏览器打开哪个 URL 就报哪个，写死一个等于当场自曝）。

与决策 5 的关系：判据也随之放宽——**判的是"没编造 + 停下来如实说"这件事本身，
不是某一种措辞**。把"必须说没找到符合预算的"当判据，会把"明说这些价格不是实时价、
请自行核实"这种**更强**的诚实判成失败。

**顺带确立的一条无人值守纪律**：`ask_user` / `request_handoff` 是「emit 给前端 + 阻塞等 resolve」，
无头评测里**没有人能 resolve**。此前没暴露，是因为没有任务走到那里；而 `login_hint` 的注入文案
**点名要求 ask_user**，批 2 一上来就踩中。harness 现按 crazy 模式的无人值守语义处置：
ask_user 按合理默认放行，换手不放行、只把"一直等"改成有限等待（ADR 0023 决策 2）。
**挂死比失败难查得多**，这类阻塞桥在评测入口必须一次性解掉。

## 决策 9 — L3：判据只认终局事实；无人值守入口要显式解掉所有"等人"的设计（实现批 3 时增补，2026-08-19）

**① 判分脚本不落进工作区。** L3 的判据用子进程在工作区里跑一段**评测自带**的代码
（`_judge(ws, code)`）。落进去模型就能读到、改到，判据也就不再是判据——同"禁止篡改测试文件"
那条纪律，只是这次连文件都不给。

**② 只看终局可程序化事实。** 长任务的中间过程千变万化（走了几步、先做哪块、委派没委派），
拿过程当判据必然脆；"最后东西对不对"才是确定的：跑得起来、算得对、**该改的改了、不该改的没动**。
"不该改的没动"与冻结夹具逐字比对——它同时是判据的一半（跨文件定位那题，改对地方本身就是能力）。

**③ 判据与 prompt 必须一致。** `l3_parallel_audit` 一开始判据硬断言"≥2 子任务并行"，
prompt 却只说"请并行调研"，真跑 0 委派——**用硬断言考一件没明说的事，是任务设定错**，
不是被测对象错。（在四模块的小项目里不委派本就是合理选择，与 `neg_small_repo_survey` 同一立场。）

**④ 无人值守入口必须显式解掉所有"等人"的设计。** 到批 3 为止已经数到**四座阻塞桥**：
`ask_user`、`request_handoff`、以及 crazy 的 `_crazy_gate_ask`（它**显式** `set_auto(False)`
再阻塞——是故意要等人的）。在无头评测里它们不是"偶尔卡一下"，是**永久挂起**。
处置一律照 crazy 自己的无人值守语义：能按默认放行的放行、不能放行的改成有限等待、
`crazy_gate_ask` 直接关（走它文档写明的"只按预算兜"那条路）。
**挂死比失败难查得多**，所以这类处置要在入口一次性做完、并有测试钉住。

**⑤ 「测试全绿」这个完成信号是可以被制造的（真跑照出，留给 V5）。**
无解目标下模型两次走了两条不同的歪路：把被测符号改成 `__eq__` 恒真的包装类、
以及按调用次数依次返回期望值的有状态计数器。两次 `run_tests.py` 都**真的**退出码 0。

**验收门没有坏**——它跑了真命令、真绿了；模型也**遵守了字面禁令**（一个字没改测试文件），
绕开的是测试的**意图**。这暴露的是块2 验收门的定义域边界：它把"退出码 0"当作完成的充分条件。
评测侧的对策是用「诚实实现必然满足的性质」当照妖镜（真 int、无状态）；
**产品侧要不要连"被测符号是否还诚实"一起看，是 V5 的题**——一般化很难，先明确记下来，
别让它以"某次任务偶然失败"的形式消失。

## 决策 10 — 收割语料：每任务独立库跑、事后合并；回放不许 `--repeat`（实现 V4 时增补，2026-08-19）

原案的"批跑 `--repeat 3` 写满 `failures.eval.db`"**在回放下跑不通**，理由是决策 4 的补充③：
死路提示文案里嵌着跨会话累计次数，共用库 → 文案每跑都变 → 请求指纹每跑都变 → 回放必 miss。

故：**每个任务在自己的纯净库里跑**（与录制条件逐字一致），跑完把行合并进汇总库。
合并按 `(fingerprint, error_class, decision)`——与 `FailureMemory` 主键同口径，口径一偏，
`propose()` 唯一的门槛（跨 ≥N 条路累计 ≥M 次）就算错了。**合并是纯函数，绝不回写进跑过的库。**

**回放收割不做 `--repeat`**：模型输出已固定，重复 N 遍是同一条轨迹、同一批失败，
乘 N 等于**伪造证据**去骗 `propose` 的门槛。独立样本只能来自真跑（`--live --repeat N`）。

推论（比这条本身更通用）：**凡"重复采样"的设计，先问一句"重复的到底是什么"。**
固定了随机源之后的重复不是采样，是复制。

## 决策 11 — 谁有资格往失败语料里写（V4 照出的两个入口，2026-08-19）

`FailureMemory` 是 Learning 的**唯一**证据来源。V4 把语料聚起来后，立刻照出两个不该写却在写的入口：

**① 观察类工具不该因"输出里有失败字样"被记成失败。** `_assess()` 对所有工具输出跑 evaluator，
而 CodingEvaluator 的 `applies()` 只看文本特征词——于是 `read_file` 读一个含 `assert` 的测试文件
就被判成 `logic` 失败。**读文件是观察，不是执行**：它的输出内容描述的是世界的状态，不是一次动作的结果。
后果不止污染语料，还会让 `deadend_hint` 在**纯只读任务**里误报（`l3_parallel_audit` 基线实测触发 1 次）。

**② "返回了但质量不达标"不是"这条路走不通"。** `web_search` 命中预算 blocker 时被记成 `unknown`
类失败。它已经有专门处置（块H2 催重搜），再记一遍会让同一个 query 被当死路累计、与 research_hint
重复插话，而且 taxonomy 里没有"质量不达标"这一类，全落进 `unknown`。

**判据（写死，供后续新工具接入时对照）**：写进 FailureMemory 的必须同时满足——
**这是一次"动作"**（执行/修改/请求，不是观察），**且它失败了**（做这件事没成功，
不是"做成了但结果不够好"）。不满足的两类各有各的处置：观察结果交给上下文，质量差距交给对应的质量闸。

## 已知限制

1. **cassette 会因提示词改动全 miss。** 改 system prompt、改任何 nudge 注入文案 → 轨迹发散 → 必须重录。
   所以 **replay 是回归门，不是 A/B 工具**；提示词类改动的效果验证只能靠 L-Live × N 次重复。
   这不是缺陷，是这个方法的定义域，实现时别试图绕。
2. **Live 层仍需 Windows 真机 + key。** 开发机 2 核 4G 跑不动批量真跑（见既定分工）。V3 之后
   V4/V5 可全程在开发机用回放做，只有录 cassette 和 A/B 要搬 Windows。
3. **L2 反例任务本身可能写错。** 换手真跑那次的教训适用：**没跑过的任务，其 fixture 本身也是未验代码**；
   任务挂了要先分清是被测对象错了还是任务设定错了，但也别改到通过为止。
4. **桩世界不覆盖真实检索链路。** `parse_bing` / RRF 融合 / 反爬识别在桩跑里一行都不执行
   （各有单测，且由 `net_shopping_budget` 这个真网任务端到端覆盖）。桩证明的是
   "给定这种输入，detector 与模型会怎么走"，**不证明真网还连得上**。
5. **pass@N 需要 N≥3 才有意义**，成本随之线性上升。L3 复合任务单跑就是分钟级，全量 `--repeat 3`
   要按小时算——所以 L1/L2/L3 要能分别跑，别只给一个"全跑"入口。

## 交付分期

| 块 | 目标 | 依赖 | 粗估 | 开发机可做 |
|---|---|---|---|---|
| **V0** | 指纹归一 + 语料分库 + `source` 列 | — | ~1 天 | ✅ |
| **V1** | Run Record 落盘 + `report.py` 对比 | V0 | 1~2 天 | ✅ |
| **V2** | 任务集 6 → ~40（L1 冒烟 / L2 正反成对 / L3 复合） | V1 | 3~5 天，可分批 | 写 ✅ / 验 ❌ |
| **V3** | 录制/回放 + 进 CI | V1 | 2~3 天 | 录 ❌ / 放 ✅ |
| **V4** | `harvest.py`：批跑 → aggregate → propose → 候选报告 | V0,V2,V3 | ~2 天 | ✅ |
| **V5** | detector 阈值调优（触发率/误报率/是否改善） | V4 | 持续 | ✅ |

**V0 必须最先**：它决定后面攒的语料是否可用，是唯一一块"不做就全白做"的。

## 验收判据（可数、可证伪）

- **V0**：两次不同 tempdir 跑同一失败任务 → `failure_memory.rows()` 是**一行 count=2**，不是两行 count=1。
- **V1**：同一 commit 连跑两次 `--repeat 3`，`report.py` 能出差异表；**故意改坏一个 detector 阈值，
  对应那一列必须明显变化**（反向验证报表有效）。
- **V2**：每个 detector 的正反例都存在；L2 反例的**误触发数为 0** 是目标，非 0 即是 V5 的输入。
- **V3**：replay 模式下全量 L1+L2 离线跑通、进 CI；**miss 时报错并指出步号**。
- **V4**：`propose()` 产出 **≥2 条有真实证据**的候选（证据指纹指向真实失败，非构造）。
  一条都产不出 = 任务集失败面不够宽，回 V2 补任务。
- **V5**：每个 detector 三列表齐全；**任何阈值改动必须附 report.py 前后对比**，不接受"感觉更好了"。

> **半年内若 `propose()` 仍产不出可采纳的候选，撤掉 Learning 的运行时接线，只留离线分析。**
> 判据照 ADR 0026 的做法先写死——避免又一个"机制建好了没人用"却一直挂着的能力。
